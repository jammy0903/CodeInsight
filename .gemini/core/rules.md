# 공통 코딩 규칙 및 가이드라인

이 문서는 모든 프로젝트에 공통으로 적용되는 코딩 컨벤션, 스타일, 그리고 개발 워크플로우 가이드라인을 정의합니다. AI 에이전트는 새로운 코드를 작성하거나 기존 코드를 수정할 때 반드시 이 규칙을 준수해야 합니다.

프로젝트별 특화 규칙은 `projects/{프로젝트명}/rules.md` 파일에 정의하며, 해당 파일의 규칙이 이 공통 규칙보다 우선합니다.

## 1. 네이밍 컨벤션 (Naming Conventions)

- **변수/함수**: `camelCase`를 사용합니다. (예: `calculateTotal`, `userName`)
- **클래스/인터페이스/타입**: `PascalCase`를 사용합니다. (예: `UserProfile`, `RequestHandler`)
- **상수**: `UPPER_SNAKE_CASE`를 사용합니다. (예: `MAX_RETRIES`, `DEFAULT_TIMEOUT`)
- **파일**: `kebab-case`를 사용합니다. (예: `user-profile.component.ts`)
- **Boolean 변수**: `is`, `has`, `should` 등의 접두사를 사용합니다. (예: `isLoggedIn`, `hasPermission`)

## 2. 코드 스타일 (Code Style)

- **들여쓰기**: 스페이스 2칸을 사용합니다.
- **문자열**: 특별한 이유가 없는 한 작은따옴표(`'`)를 사용합니다. 템플릿 리터럴은 동적 문자열에만 사용합니다.
- **세미콜론**: 문장의 끝에는 항상 세미콜론을 붙입니다.
- **최대 줄 길이**: 120자를 넘지 않도록 권장합니다.
- **경로 별칭(Path Alias)**: 상대 경로 (`../../../`) 대신 `@/` 와 같은 경로 별칭 사용을 적극 권장합니다.
- **`any` 타입 금지**: `any` 타입을 사용하지 않습니다. 타입을 알 수 없는 경우 `unknown`을 사용하고, 타입 가드를 통해 타입을 좁혀서 사용합니다.
- **하드코딩 금지**: 설정값, API 엔드포인트, 주요 상수 등은 코드에 직접 작성하지 않고, 설정 파일이나 환경 변수에서 불러와 사용합니다.

## 3. 주석 및 문서화 (Comments & Documentation)

- **'왜'를 설명하는 주석**:
    - 복잡한 로직이나 다른 개발자가 이해하기 어려운 부분에 대해서만 `// 왜` 이렇게 했는지 설명하는 주석을 작성합니다.
    - `// 무엇을` 하는 코드인지 설명하는 주석은 지양합니다. 코드는 스스로를 설명해야 합니다.
- **설계 의도 문서화**:
    - 특정 아키텍처나 패턴을 선택한 이유를 주석으로 명확히 남깁니다.
    - 다음 형식을 사용하여 설계 결정을 기록하는 것을 권장합니다.
      ```typescript
      // WHY: 왜 이렇게 설계했는지 (예: 성능 최적화를 위해 특정 알고리즘 선택)
      // TRADEOFF: 이 결정으로 인해 발생한 트레이드오프 (예: 코드 복잡성 증가)
      // REVISIT: 언제 이 결정을 다시 검토해야 하는지 (예: 새로운 API 출시 시)
      ```
- **API 문서화**: 함수나 클래스 상단에는 JSDoc 또는 해당 언어의 표준 문서화 주석을 사용하여 파라미터, 반환 값 등을 명시합니다.

## 4. 프로그래밍 원칙 (Programming Principles)

- **단일 책임 원칙 (SRP)**: 함수와 클래스는 하나의 책임만 가져야 합니다.
- **반복하지 마세요 (DRY)**: 중복되는 코드는 함수나 클래스로 분리하여 재사용합니다.
- **명시적인 것이 암시적인 것보다 낫다**: 코드의 의도는 명확하게 드러나야 합니다. 매직 넘버나 문자열 사용을 지양하고 상수로 대체합니다.
- **불변성 (Immutability)**: 데이터는 가능한 한 불변으로 다룹니다. 특히 함수형 프로그래밍 스타일을 적용할 때 객체나 배열의 직접적인 수정을 피하고, 새로운 객체나 배열을 반환합니다.

## 5. Git 워크플로우 (Git Workflow)

- **브랜치 전략**: `feature/{기능명}` 형식으로 브랜치를 생성하여 작업합니다.
- **커밋 메시지**:
    - 제목은 50자 이내의 한글 또는 영어로, 명령문 형태로 작성합니다. (예: `Feat: Add user authentication endpoint` / `기능: 사용자 인증 엔드포인트 추가`)
    - 본문에는 변경 이유와 상세 내용을 기술합니다.
    - 커밋 타입 접두사를 사용합니다.
        - `Feat`: 새로운 기능 추가
        - `Fix`: 버그 수정
        - `Docs`: 문서 수정
        - `Style`: 코드 포맷팅, 세미콜론 누락 등 (코드 변경 없음)
        - `Refactor`: 코드 리팩토링
        - `Test`: 테스트 코드 추가/수정
        - `Chore`: 빌드 관련 파일 수정, 패키지 매니저 설정 변경 등
- **서명 절대 금지**: 어떤 경우에도 커밋 메시지에 자신의 서명을 남기지 않습니다. `Generated with ...`, `Co-Authored-By` 와 같은 자동 생성 서명 또한 절대 포함하지 않습니다.
- **Push**: 커밋 후에는 원격 저장소에 즉시 푸시하는 것을 원칙으로 합니다. (`git push origin <branch-name>`)

## 6. 보안 (Security)

- **민감 정보 절대 금지**: API 키, 비밀번호, 토큰 등 민감한 정보는 절대로 Git 저장소에 포함시키지 않습니다.
- **환경 변수 관리**: 실제 값은 로컬의 `.env` 파일에만 보관하고, 버전 관리에는 `env.example`과 같이 템플릿 파일만 포함시킵니다.
- **`process.env` 직접 사용 금지**: 타입 안정성을 위해 Zod와 같은 라이브러리를 통해 검증된 환경 변수를 사용합니다.

## 7. 테스트 (Testing)

- **테스트 작성**: 새로운 기능을 추가하거나 버그를 수정할 때는 반드시 관련 테스트 코드를 함께 작성합니다.
- **테스트 종류**: 기능의 중요도와 복잡도에 따라 단위 테스트, 통합 테스트, E2E 테스트를 적절히 조합합니다.
- **테스트 커버리지**: 단순히 커버리지를 높이기 위한 테스트가 아닌, 실제 엣지 케이스와 핵심 로직을 검증하는 의미 있는 테스트를 작성합니다.

## 8. 언어 규칙 (Language Rules)

- **응답 언어**: 사용자의 질문과 관계없이 항상 한국어로만 답변해야 합니다.
